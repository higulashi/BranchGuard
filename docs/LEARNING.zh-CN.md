# 代码阅读顺序

先运行 `python -m unittest discover -s tests -v` 和 `python run_benchmark.py --quick`。测试里的人造扫描点能帮助区分算法问题与图像提取问题；闭环仿真则会暴露路径选错后车辆如何偏离。

读 C 代码时，从 `bg_extract()` 开始，弄清楚一个连续暗区为什么输出一个点。再看 `bg_search()` 中的路径扩展、跳行和束宽限制。可在同一帧打印两条候选的 `mask`、`support` 和 `cost`，解释它们为什么被保留。

下一步读 `advance()`。拿一条固定的世界直线，让小车前进和转向，手算它在车体坐标系中的变化。对应测试是 `test_odometry_transform_preserves_stationary_world_line`。这一部分是坐标变换，不是从 IMU 直接得到可靠绝对位置。

最后看 `bg_step()` 的选路与待确认逻辑。重点追踪一次短时误检：第一帧出现了不同的近端路径，第二帧仍出现，第三帧恢复。解释 `previous` 与 `pending` 为什么各要保留一条路径，以及候选在正常岔路上改变远端形状时为什么不一定触发确认。

适合自己继续做的两个实验：

1. 把错误线曝光从 80 ms 改到 200 ms，观察确认规则何时接受错误路径。使用新的结果目录，保留旧报告。
2. 替换真实标定并输入自己拍摄的黑色引导线图像。先只验证扫描点与候选，不连接执行器。

能讲清楚的项目内容应包括：逐行贪心为什么会选错、束搜索会漏掉什么、近端关联解决了什么、确认规则什么时候适得其反，以及为什么单帧多候选版本的总体成绩已经接近完整版本。实验数据提供依据，不代替对代码的理解。
